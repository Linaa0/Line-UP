# Architecture

Line-Up is a **monorepo with two independent applications**. They share no
code and no `node_modules`; each has its own `package.json`, lockfile,
TypeScript config and env file. They communicate only over HTTP (REST/JSON).

```
┌──────────────────────┐   HTTPS / JSON   ┌──────────────────────┐   Prisma   ┌────────────┐
│ frontend (Next.js)   │ ───────────────▶ │ backend (NestJS)     │ ─────────▶ │ PostgreSQL │
│ localhost:3000       │  /api/v1/...     │ localhost:4000       │            │            │
└──────────────────────┘                  └──────────────────────┘            └────────────┘
```

## Frontend — `frontend/`

Next.js (App Router) · React · TypeScript · Tailwind CSS v4 · shadcn/ui.

```
frontend/src/
├── app/                 # Routing only: layouts, pages, route groups
│   ├── (marketing)/     # Public pages (landing, about)
│   ├── (auth)/          # Sign-in / sign-up / verification
│   ├── (passenger)/     # Signed-in passenger app (home, tickets, …)
│   ├── layout.tsx       # Root layout: fonts, metadata, <html>/<body>
│   └── globals.css      # Tailwind import + design tokens (CSS variables)
├── components/
│   ├── ui/              # shadcn/ui primitives (Button, Input, …)
│   ├── layout/          # App shell pieces (page container, headers)
│   ├── navigation/      # Bottom tab bar, back-header, menus
│   └── shared/          # Cross-feature composites (empty state, badges)
├── features/<feature>/  # Everything specific to one feature
├── hooks/               # Generic React hooks shared across features
├── lib/                 # Library setup & helpers (cn(), env, api client)
├── services/            # Cross-feature API clients
├── types/               # Shared TypeScript types
├── constants/           # App-wide constants
└── utils/               # Pure, framework-free helper functions
```

**Rules**

- `app/` files stay thin: a page imports a screen component from its
  feature and renders it.
- A feature folder owns its components, hooks, API calls and types:
  ```
  features/tickets/
  ├── components/
  ├── hooks/
  ├── api.ts
  └── types.ts
  ```
  Create sub-folders only when the feature needs them.
- Code moves to `components/shared`, `hooks/` or `lib/` only once a second
  feature needs it.
- Route groups `(…)` organise layouts without affecting URLs.
- Path alias: `@/*` → `src/*`.

## Backend — `backend/`

NestJS · TypeScript · REST · Prisma · PostgreSQL.

```
backend/src/
├── main.ts              # Bootstrap: creates the app and listens on PORT
├── app.setup.ts         # Global prefix /api, URI versioning (v1), CORS — shared with e2e tests
├── app.module.ts        # Root module: wires config, database, feature modules
├── config/              # Env schema + validation (fails fast on bad config)
├── database/            # PrismaService / PrismaModule (global)
├── common/              # Cross-cutting: filters, guards, interceptors, DTO helpers
├── health/              # GET /api/v1/health
├── auth/ users/ routes/ stops/ buses/ trips/ fares/
├── tickets/ payments/ queues/ notifications/   # Domain modules (to be built)
backend/prisma/
├── schema.prisma        # Data model (datasource + generator only for now)
├── migrations/          # Generated by `prisma migrate dev`
└── seed.ts              # Development seed script
backend/prisma.config.ts # Prisma CLI config: schema path, migrations, seed, DATABASE_URL
backend/src/generated/   # Generated Prisma Client (git-ignored, `npm run prisma:generate`)
```

**Rules**

- One NestJS module per domain folder: `*.module.ts`, `*.controller.ts`,
  `*.service.ts`, `dto/`. Generate with `npx nest g resource <name>`.
- Controllers handle HTTP only; business logic lives in services; database
  access goes through `PrismaService`.
- All routes are prefixed `/api` and versioned (`/api/v1/...`).
- Request input is validated with **zod** schemas via Nest's
  `StandardSchemaValidationPipe` (`@Body({ schema })`) — the same library used
  for env validation, so no class-validator/class-transformer is needed.
- The backend is **ESM** (NestJS 12): relative imports end in `.js`, tests
  use Vitest (`vi.fn()`), linting uses oxlint.
- Configuration is read only through `ConfigService`; the schema in
  `src/config/env.validation.ts` is the single list of allowed variables.

## External integrations

None yet. Payment providers (e.g. MTN MoMo, Airtel Money), maps/live
location and SMS/push notifications will be added as real integrations
behind dedicated backend modules — no fake or mock integrations that
pretend to be real.
